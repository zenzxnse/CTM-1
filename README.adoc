= Context HMI

Context HMI is a reusable local-first service that turns reviewed machine context
and an operator request into a validated declarative HMI view. It is an advisory
layer, not a PLC safety system, control authority, or vendor-runtime replacement.

== Supported workflow

. Load a bounded, versioned machine model with explicit asset, tag, role, unit,
  relationship and alarm metadata.
. Create that model from reviewed engineering artifacts and explicit mapping
  decisions, retaining provenance and unresolved fields.
. Ingest current telemetry from an external source through the JSON API.
. Retrieve only the relevant model subgraph for the operator request.
. Interpret through deterministic rules, an optional local llama.cpp endpoint, or
  an explicitly enabled OpenAI-compatible provider.
. Validate the finite task proposal and resolve bindings in C++.
. Return a versioned JSON screen with catalog components, values, quality,
  freshness, binding evidence and issues.
. Reconcile saved views when the model revision changes.

Provider calls are bounded and observable. Retrieval and interpretation caches are
finite, TTL-bound and keyed by model identity, revision, generation, provider and
normalized request. Cache hits, context size, candidate scope, truncation, provider
usage and timings are exposed for engineering review. Telemetry remains available
when inference is unavailable.

== Quick start

Prerequisites are CMake 4.x, a C++20 compiler, Ninja, Node.js 22.12 or newer and
Python 3.11 or newer. Native build and execution are owned by the release process.

[source,shell]
----
npm --prefix workbench ci
npm --prefix workbench run build
cmake --preset debug
cmake --build --preset debug --parallel 2
./build/linux-debug/context-hmi --config config/context-hmi.json \
  --web-dir workbench/build \
  --model examples/machines/assembly-line.json \
  --models examples/machines
----

Open http://127.0.0.1:8080[the local workbench]. Enter a request such as
`Show the status of the packaging line`. Post a current telemetry batch to
`/api/v1/telemetry` and inspect the generated view and execution metadata.

== API and configuration

The HTTP API is versioned under `/api/v1` and uses JSON envelopes. The important
routes are `GET /health`, `GET /session`, `GET /ready`, `GET /model`,
`GET /catalog`, `GET /scenarios`, `GET /metrics`, `GET /telemetry`, `GET /events`,
`GET /audit`, `GET /records`, `POST /context/retrieve`, `POST /telemetry`,
`POST /interpret`, `POST /resolve`, `POST /reconcile` and `POST /scenario`.
See link:docs/api.adoc[the API contract].

The service configuration is JSON and validated against
link:schemas/service-config.schema.json[the schema]. The orchestration file is
YAML and is not parsed as application configuration. Secrets are environment or
file references only. See link:config/deployment.yaml[the deployment profile] and
link:docker/README.adoc[container instructions].

== Product boundary

The JSON model and screen contract are vendor-neutral. Engineering artifacts are
the input to reviewed context creation; product-specific runtime integration is
outside the active release. The screen is composed dynamically from the selected
task and adapts through a responsive layout contract, with no predesigned screen
set or generated executable UI. Qt can consume the same screen contract in a
future client.

To create a model from a reviewed engineering bundle, use the context importer:

[source,shell]
----
./build/linux-debug/context-hmi-context --bundle examples/artifacts \
  --output build/assembly-line-import-result.json
jq '.model' build/assembly-line-import-result.json > build/assembly-line.json
----

Review the import report before supplying the extracted model to the service. The
importer never derives ownership or relationships from names, paths or protocol
addresses.

The service uses Drogon for HTTP and the framed operational journal for required
records. It does not use SQLite. Diagnostic logs, operational records, current
telemetry and benchmark results are separate concerns.

== Verification

Run the workbench checks, native Debug and Release suites, sanitizer profile,
package smoke checks and platform-specific jobs from the repository workflow.
Raw benchmark JSON is preserved and plots are generated only from measured data:

[source,shell]
----
python3 benchmarks/live.py --build-dir build/linux-release \
  --save build/benchmarks/live.json
python3 benchmarks/plot.py --live build/benchmarks/live.json \
  --output build/benchmarks/context-hmi.svg
----

Cross-compilation, Docker Desktop execution and a Linux container health check do
not establish native Windows, Windows Server, TCL display, vendor-runtime or
industrial-controller compatibility. Evidence is labelled accordingly.
