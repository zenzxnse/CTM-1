= Architecture

This document describes the active standalone service and its evidence boundary.

== Boundaries

The C++ engine owns model validation, relevant-context retrieval, interpretation
checks, deterministic binding resolution, screen composition, telemetry freshness
and model reconciliation. The Drogon service owns HTTP lifecycle, bounded requests,
sessions and event streams. A framed operational journal stores required records;
structured diagnostic logging is separate and may drop low-severity entries on
overflow. Current telemetry is neither an audit log nor a historian.

The SvelteKit workbench renders a fixed component catalog from server-owned JSON. It
does not resolve source addresses, execute generated code, hold provider keys or
grant command authority. A future Qt client can consume the same contract.

== Request path

. Parse reviewed engineering artifacts into a versioned machine model, retaining
  provenance and unresolved fields, then validate explicit identities and metadata.
. Accept a bounded current telemetry batch from an external source.
. Normalize the request and retrieve a relevant model subgraph.
. Return clarification for no candidate or equal candidates.
. Check the interpretation cache or call the selected bounded provider.
. Validate the finite task against the current model and retrieval candidates.
. Resolve declared tags, compose a declarative view and publish execution evidence.
. Re-evaluate saved views when model generation or revision changes.

Screen composition is task-driven. The service selects reviewed catalog components
from the current model and returns a responsive layout contract; clients adapt that
contract to their viewport rather than relying on predesigned screens or generated
executable UI code.

Stable provider instructions and schema precede variable context and user input to
support exact-prefix provider caching. Native caches are bounded, TTL-bound and
invalidated by model changes. A cache hit still performs current native validation
and binding resolution.

== Failure behavior

Inference failure leaves the service, current views and telemetry available. Empty,
unknown or stale values are explicit. A missing or changed binding is marked
unavailable or needs review. A provider response outside retrieved candidates is an
interpretation mismatch. A generation change returns a stale-context result instead
of publishing a view based on an old model. Reconnect and rescan behavior is handled
by the source that posts telemetry; source freshness remains visible to clients.

== Supported and excluded scope

The supported source boundary is a versioned JSON model created from reviewed
engineering artifacts plus external telemetry ingestion. Product-specific runtime
integration remains outside the active release. The release includes no simulator,
protocol adapter, native display renderer, physical command route or executable UI
generation. These exclusions keep the reusable interpretation and rendering contract
small enough to verify.

== Evidence

Build profiles cover CMake 4.x Linux, constrained Linux, native Windows and Windows
Server jobs. A cross-build proves compilation only. A Docker Desktop run proves the
Linux container profile only. Vendor compatibility requires a named product version,
reviewed artifact or endpoint, and a real execution test. See
link:evidence-conventions.adoc[evidence conventions] and
link:platforms.adoc[platform support].
