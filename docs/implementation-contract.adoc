= Standalone implementation contract

Status:: Accepted active contract
Date:: 2026-09-11

== Scope

The service loads a reviewed machine model, ingests current external telemetry,
interprets bounded operator requests, composes declarative views and reconciles
those views after model revisions. Rules are always available. llama.cpp and
OpenAI-compatible providers are explicit options. The LLM proposes only a finite
task; native code owns all identity, binding, validation and permission decisions.

== Model envelope

The model contains `model_id`, non-negative `revision`, `name`, `assets`,
`relationships`, `tags` and `alarms`. Every asset and tag has a stable declared
identity. Every tag names its owning asset, role, type, unit and source reference.
Relationships and alarm ownership are explicit. Names, paths and source addresses
are not proof of ownership. Semantic same-ID changes are conflicts during
reconciliation.

== Telemetry envelope

`POST /api/v1/telemetry` receives `context-hmi-telemetry/1` with model identity,
revision, context generation, source ID, sequence and bounded tag values. Each value
carries its value, quality and unsigned source timestamp in milliseconds; its declared
type comes from the matching model tag. The service atomically validates and replaces
the current batch. It marks stale values from receive age and preserves unknown values
for missing tags.

== Task and view

Tasks contain a supported finite `kind`, model identity and revision, original
request and optional anchor asset. Retrieval evidence precedes interpretation and
contains candidates, reasons, direct relationships, owned tags, alarms, byte size,
estimated tokens and truncation. A view contains a server-generated `view_id`, task,
catalog components, resolved bindings, live values, issues and dependency
fingerprints. Clients render the contract and never execute generated source.
Components are selected from the task and retrieved context at request time. The
view also carries responsive layout metadata so a client can adapt the same screen
contract across display sizes without relying on a predesigned screen set.

== Provider contract

Providers receive static instructions and the output schema before bounded variable
context and the operator request. A provider response must be a typed ready task or
clarification. Native validation rejects unknown properties, unsupported kinds,
model mismatch, stale generation and selections outside retrieved candidates.
Provider usage is optional and must be surfaced as unavailable when absent.

== HTTP routes

All routes are under `/api/v1`: `GET /health`, `GET /session`, `GET /ready`,
`GET /model`, `GET /catalog`, `GET /scenarios`, `GET /metrics`, `GET /audit`,
`GET /records`, `GET /telemetry`, `GET /events`, `POST /context/retrieve`,
`POST /telemetry`, `POST /interpret`, `POST /resolve`, `POST /reconcile` and
`POST /scenario`. Errors use the stable
`{error:{code,message}}` envelope. Bodies, depth, prompts, telemetry, provider
concurrency, streams and caches are bounded.

== Clients and safety

SvelteKit is the primary client. A future Qt client may consume the same JSON screen
contract. No client receives credentials or controller addresses for rebinding. The
active scope has no physical command route. Any future control action requires a
separate accepted contract with identity, authorization, freshness, idempotency,
approval and observed feedback.
