= Prototype demonstration

All demonstrations use simulated equipment. Start the native service with the built
workbench and the original `examples/pump-station.json` model.

[cols="1,2,2",options="header"]
|===
|Step |Action |What to inspect
|1 |Request `Show the filling view for Tank 3` |Task scope, tank level, declared feed data and alarms.
|2 |Open `Why this reading?` and `Inspect bindings` |The reason and authoritative tag owner for each component.
|3 |Select `Add a second feed` |Additional components come from the new declared feed relationship.
|4 |Return to the original model and make a fresh request |A clean saved interpretation for the next test.
|5 |Select `Move a flow tag owner` |The existing flow reading becomes conflicted even though its tag ID still exists.
|6 |Select the same changed configuration again |The conflict remains visible and its reading stays unavailable.
|7 |Make a fresh request on the original model, then remove its level reading |Missing required context is explicit.
|8 |Select `Ambiguous equipment name` and request `Show filling for third tank` |The interpreter asks for clarification.
|9 |Select the second machine and request `Show filling for Buffer A` |Different equipment identities use the same task resolution path.
|10 |Pause the simulator or disconnect the backend |The client displays unknown values rather than healthy-looking stale readings.
|===

== Interpretation modes

The default deterministic mode supports a limited vocabulary. It is labelled `Rules`.
It is useful for demonstrating the context engine without model installation or network access.

Local AI mode requires a separately running llama.cpp server and compatible model.
The provider still returns a typed task through the engine's validation boundary.
Do not describe rules-mode success as LLM interpretation accuracy.

== Evaluation still required

The checked-in examples exercise the mechanism. They are authored fixtures, not an
unseen plant trial. The second machine is also part of the test suite and must not be
presented as independent validation data after tuning against it.

A future comparison should give a competent template/query implementation the same
machine metadata and tasks. Count metadata preparation, task authoring and revision
maintenance for both approaches. Record correct updates, wrong acceptances, unnecessary
rejections and unknown results separately. No superiority result is established here.
