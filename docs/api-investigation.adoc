= API investigation for PS2 integration

Date:: 2026-09-10

Status:: Research note for the prototype. The links below are the primary
documentation or source checked on the date above. A statement marked
`doc only` was not exercised against a live device, runtime, vendor SDK, or
llama.cpp binary.

== Findings at a glance

* The current service is a simulation service. There is no OPC UA client,
  Schneider runtime connection, physical command path, or installed vendor
  SDK in this workspace.
* open62541 exposes the client services needed for a future read, browse, and
  subscription adapter. The library is a C API callable from C++ and the
  client has no worker thread of its own.
* llama.cpp's HTTP server documents schema-constrained JSON. The local
  implementation uses its `/v1/chat/completions` route, but no live llama.cpp
  server was available for a compatibility test.
* Schneider's public pages document in-project HMI scripting and variable
  binding. I found no public, versioned external SDK contract for importing a
  generated screen, controlling a runtime, or attaching a C++ service to
  EcoStruxure Operator Terminal Expert or Machine SCADA Expert. Treat that
  access as unknown until the exact product, release, and licensed SDK are
  supplied.

== open62541

The official https://open62541.org/doc/master/client.html[open62541 client documentation]
states that the client does not start its own thread. The application must
call `UA_Client_run_iterate` periodically to process asynchronous events,
connection housekeeping, and subscriptions. The same page documents the
high-level functions below and their raw service equivalents:

* connect with `UA_Client_connect`, then use `UA_Client_run_iterate` and end
  with `UA_Client_disconnect`;
* browse with `UA_Client_browse`, continue a paged browse with
  `UA_Client_browseNext`, or use `UA_Client_translateBrowsePathToNodeIds`;
* read a value with `UA_Client_readValueAttribute`;
* create a subscription with `UA_CreateSubscriptionRequest_default` and
  `UA_Client_Subscriptions_create`;
* create a value monitored item with
  `UA_MonitoredItemCreateRequest_default` and
  `UA_Client_MonitoredItems_createDataChange`; the documented callback receives
  the `UA_DataValue`, including its status and timestamps.

The documentation says subscriptions are asynchronous and that a subscription
reports notifications generated by its monitored items. It also warns that a
notification can be processed before the create response is received. The
adapter must therefore tolerate an early initial value and must check the
server-adjusted sampling and publishing parameters.

The https://open62541.org/doc/master/types.html[open62541 data type documentation]
states that a `NodeId` carries a namespace index, while the server's
`NamespaceArray` maps namespace URIs to indices. Indices are not stable across
servers. The client documentation provides `UA_Client_getNamespaceIndex` and
`UA_Client_getNamespaceUri`, and says the client reads the server namespace
array on connect. The model must therefore persist the namespace URI and
identifier, not a namespace index alone. Resolve the URI to an index after
each connection. For a string, numeric, GUID, or byte identifier, preserve the
identifier type as well as its value when serializing a source reference.

For the optional next slice, pin the adapter to the released
https://github.com/open62541/open62541/releases/tag/v1.5.8[open62541 v1.5.8 release]
and compile against the matching
https://github.com/open62541/open62541/blob/v1.5.8/include/open62541/client.h[`open62541/client.h`]
and
https://github.com/open62541/open62541/blob/v1.5.8/include/open62541/client_highlevel.h[`open62541/client_highlevel.h`]
headers. The client documentation above is the source for the namespace mapping
and `NamespaceArray` behavior. The exact header build and a connection to a real
server remain untested here.

== llama.cpp local HTTP provider

The primary
https://github.com/ggml-org/llama.cpp/blob/9cffdcc801582616250520966699cb5b25d28243/tools/server/README.md[pinned llama.cpp server README]
documents `POST /v1/chat/completions`, synchronous and streaming responses,
and a `response_format` option for JSON and schema-constrained JSON. It also
documents command-line `--json-schema` and `--json-schema-file` options and
notes that only supported model chat templates work optimally.

The README's examples use a `response_format` object with `type` set to
`json_object` or `json_schema` and a schema member. The official
https://github.com/ggml-org/llama.cpp/blob/9cffdcc801582616250520966699cb5b25d28243/tools/server/server-common.cpp#L1168-L1178[pinned server source]
shows the `json_schema` response format being read as a wrapper and then taking
its nested `schema` member. The current local provider therefore posts the
OpenAI-style nested object to a loopback URL, sends declared machine context in
the prompt, requests `type: json_schema`, and validates the returned
interpretation before binding it to a view. This provider behavior is covered
by local mock HTTP shape tests only. It has not been tested against a live
llama.cpp binary or model.

The provider must remain an interpretation provider. It cannot select a tag by
name alone, manufacture an owner, or issue a protocol command. The core still
validates the returned task and resolves it against the declared model.

== Schneider EcoStruxure HMI products

The exact product boundary is unresolved because “EcoStruxure HMI” can mean
at least Operator Terminal Expert or Machine SCADA Expert, with release and
target runtime affecting the integration surface.

Schneider's https://www.se.com/us/en/faqs/FA410870/[Operator Terminal Expert visibility FAQ]
documents Blockly scripting, converters, and binding a BOOL variable to an
object property. This is evidence of an in-project scripting and binding
surface. It does not document an external project file schema, a public
screen-generation SDK, a C++/.NET runtime API, or a runtime control endpoint.

Schneider's https://www.se.com/sg/en/faqs/FAQ000141925/[Machine SCADA Expert license FAQ]
identifies the product and links its product documentation and software
downloads. It is a licensing article, not an automation API specification.
The public Schneider pages checked here did not expose a versioned import,
extension, or runtime API for this prototype to call. Access to the product
help site and any licensed SDK should be verified manually on the target
Windows installation before designing an adapter. Until then, the prototype
must present its SvelteKit workbench and local HTTP API as its supported UI
surface and keep Schneider integration as a future adapter with an explicit
unknown status.

== Metadata and ownership boundary

The implementation contract already separates an asset identity from a source
reference. A real adapter must preserve that separation:

* `asset_id` is the model owner and is never inferred from an OPC UA folder,
  browse name, or HMI tag name;
* `tag_id`, `role`, `data_type`, and `unit` come from the declared model;
* `source.server`, `source.namespace_uri`, and a typed source identifier select
  the external value; a resolved namespace index is connection-local;
* every read or notification is translated to the declared tag and owner and
  carries quality/status and source/server timestamps where available;
* an unknown, changed, or removed source reference yields unavailable or
  needs-review state. It does not silently rebind to a similarly named node.

== Evidence and limits

The open62541 statements above are doc only, based on the linked primary
documentation and release page. The llama.cpp request shape is source-inspected
against the pinned server source, but remains untested against a live binary.
Local inspection confirms that this
workspace implements the simulator, deterministic rules provider, optional
loopback llama.cpp provider, bounded telemetry SSE, and model reconciliation;
there is no live OPC UA or Schneider integration to test. No vendor Windows
runtime, product project, or licensed Schneider SDK was available, so no claim
is made about import formats, extension points, runtime automation, or product
compatibility.
